# /dev/host Virtualization Architecture

## Overview

This document outlines the architecture for the `/dev/host` virtual filesystem (VFS) in the `washm` project. The goal is to provide a mechanism for the WASM guest to interact with the host environment (JavaScript) without relying on the host's real filesystem.

## Core Principles

1.  **Absolute Paths Only**: All references to the virtual filesystem must use absolute paths starting with `/dev/host`. Relative paths (e.g., `dev/host/...`) are strictly forbidden for VFS access to ensure clarity and avoid ambiguity with the guest's current working directory.
2.  **Pure Virtualization**: The `/dev/host` hierarchy is completely virtual. It **MUST NOT** be mapped to any real directory on the host filesystem. No files or directories will be created on the host disk for these paths.
3.  **No Special Preopens**: The host **MUST NOT** preopen a specific directory to serve `/dev/host`. The WASI layer in the host will intercept paths starting with `/dev/host` before they reach the underlying WASI implementation or the real filesystem.
4.  **Object-Based Mapping**: The virtual filesystem maps directly to a JavaScript object structure rooted at `globalThis.mounted`.

## Implementation Details

### Host Side (`axy.js`)

*   **Root Object**: A global object `globalThis.mounted = {}` will be initialized on startup.
*   **Path Interception**: The WASI import wrappers (`path_open`, `fd_read`, `fd_write`, `fd_close`, etc.) will check if a path starts with `/dev/host`.
    *   If it does, the operation is routed to the `mounted` object.
    *   Path segments map to object properties: `/dev/host/a/b` maps to `globalThis.mounted.a.b`.
*   **Subsystems**:
    *   **Eval**: The `eval` subsystem will attach a `Proxy` to `globalThis.mounted.eval`. This proxy will handle dynamic file creation (e.g., `/dev/host/eval/<cookie>.js`) to execute JavaScript code and return results.
    *   **State**: Host state (like startup PWD) will be exposed via plain objects, e.g., `globalThis.mounted.washm = { start_pwd: ... }`.
*   **Exit Handling**: Guest exit requests should ideally be handled via `eval('process.exit(code)')`. If file-based coordination is required, it must use a virtual file (e.g., `/dev/host/washm/exit_code`) and not a real file on the host disk.

### Guest Side (Rust)

*   **Absolute Paths**: All Rust code interacting with the host must use `Path::new("/dev/host/...")`.
*   **No Fallbacks**: Code should not fall back to relative paths or environment variables if the VFS path is expected to work.

## Restrictions and Commitments

To ensure system integrity and stability, the following restrictions are strictly observed:

1.  **No Git Submodule Modifications**: No changes will be made to files inside git submodules (e.g., `brush-fork`, `coreutils-fork`) directly. Any necessary changes must be handled via patches or upstream contributions.
2.  **No Arbitrary Preopens**: The host will not preopen arbitrary directories to facilitate VFS access. Only standard roots (like `.`) are preopened.
3.  **Strict VFS Isolation**: `/dev/host` traffic is strictly isolated from the real filesystem.
4.  **Timeout Management**: Host execution in tests or scripts should use timeouts to prevent hanging processes during development.

## Migration Plan

1.  **Initialize `mounted`**: Add `globalThis.mounted` initialization in `axy.js`.
2.  **Implement Interceptors**: Update `axy.js` to intercept `/dev/host/*` absolute paths.
3.  **Update Rust Code**: Refactor `src/wasm_async.rs`, `src/uutils_bridge.rs`, and other call sites to use absolute `/dev/host` paths.
4.  **Verify**: Ensure `pwd` returns the host PWD (via `mounted.washm.start_pwd`) and `eval` works correctly.
