This specification outlines the transition of the `build.rs` rewrite engine from regex/string-matching to a semantic model using `rust-analyzer` (RA).

### 1. Objective

Replace the current brittle 350+ lines of path-patching and regex replacements with a **Semantic Transformation Engine**. This engine must programmatically resolve module hierarchies and update `crate::` references based on their new position in the project's module tree.

### 2. Execution Environment: Deadlock Avoidance

The primary implementation constraint is preventing Cargo lock contention.

* **Target Directory Redirection:** The tool must programmatically set `CARGO_TARGET_DIR=target/ra-rewrite` (or a similar isolated path) before initializing the RA `ProjectWorkspace`.
* **Reasoning:** If RA attempts to discover the project using the default target directory, it will attempt to acquire the same `package-cache` lock held by the currently running `cargo build`. This results in a permanent deadlock.
* **Implementation:** ```rust
std::env::set_var("CARGO_TARGET_DIR", "target/ra-rewrite");
// Only then initialize ProjectWorkspace::load
```


```



### 3. The Dual-Graph Architecture

The implementation must maintain two concurrent views of the codebase to bridge the gap between "Source" and "Target" states.

* **Source View (The "Shadow Graph"):**
* Initialize an `AnalysisHost` and load the upstream fork directories (e.g., `brush-fork/brush-core/src/lib.rs`) into the Virtual File System (VFS).
* **Constraint:** These must be defined as valid `CrateRoot` entities in a temporary `CrateGraph`. This allows RA to resolve references like `crate::tty_helpers` (referring to sibling files in the fork) within the fork's own context.


* **Target View (The "Project Graph"):**
* Initialize the host project's `CrateGraph`.
* **Transformation:** Attach the files in `target/vendor/` not as crates, but as `Module` nodes under the host project’s root crate.



### 4. Core Transformation Requirements

#### A. Semantic Re-rooting (Fixing `crate::` paths)

The team must implement a pass that updates internal paths.

* **Problem:** Code in `target/vendor/brush-core/main.rs` that says `use crate::tty_helpers;` will fail because it now looks for `tty_helpers` at the host project's root.
* **RA Solution:** 1. Identify the original `FileId` of the reference in the Shadow Graph.
2. Query the Project Graph for that `FileId`'s new position relative to the host root.
3. Programmatically rewrite the path to its qualified form: `crate::brush_core::tty_helpers`.

#### B. Automated Path Synthesis

Replace the manual `pathdiff` and `replace("\\", "/")` logic.

* **Logic:** When a `mod` declaration in the Project Graph refers to a file that remains physically located in the `brush-fork/` directory, the engine must use RA’s `SourceMapper` to calculate the distance.
* **Output:** Automatically emit the `#[path = "..."]` attribute based on the VFS location.

#### C. Type-Aware Structural Search and Replace (SSR)

Replace the `ast_grep_replace_batch` with RA's SSR.

* **Requirement:** Target specific patterns like `NotSupportedOnThisPlatform($msg)` only when they originate from the vendored error types.
* **Validation:** Retain the `verify_no_stubs` check to ensure the final disk output is clean.

### 5. Implementation Directives

1. **VFS-to-Disk Sync:** Perform all transformations in the VFS memory first. Only write to `target/vendor/` once the semantic model is consistent.
2. **Reference Case:** The implementation is successful when `crate::` references in the vendored shell resolve to their siblings in the `target/vendor` tree without manual string manipulation or regex guessing.

### 6. Line Count Target

The implementation should reduce the total line count of `build.rs` from ~460 lines to approximately **250 lines** by centralizing all patching logic into a single semantic loop, while shifting the complexity into the RA initialization boilerplate.
