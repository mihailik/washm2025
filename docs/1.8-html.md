# HTML-Hosted WASHM Shell Implementation Plan

This document outlines the architecture and implementation steps for running the WASHM shell in a browser environment. The design prioritizes a minimal, polyglot host launcher and delegates platform adaptation to the Rust/WASM guest via dynamic bridge injection.

## Core Principles

1.  **Polyglot Launcher**: `washm.js` is a single file that runs in both Node.js and the Browser. It provides the minimal WASI environment required for the Rust guest to boot.
2.  **Minimal Host**: The HTML entry point is strictly minimal. No UI logic, styles, or heavy frameworks exist in the host.
3.  **Guest-Driven Adaptation**: The Rust guest detects its environment and injects the appropriate "bridge" (JS payload) to adapt to the platform.
4.  **Unified Bootstrap**: The FD 20251219 eval protocol is the single mechanism for host-guest communication during startup, consistent across Node and Browser.

## Architecture Components

The current implementation of WASHM in Node.js relies on several non-trivial decisions, that are highly relevant in context of the implementation of WASHM for HTML.

* **async raw stdio:** WASHM does not use synchronous stdio reads in any code path, instead relying on async reads with raw mode enabled; this is relevant in the current WASHM+node host, and makes codebase ready for browser with minimal changes
* **JS loading with sourceURL:** WASHM injects JS code into the host via eval, and uses `//# sourceURL=` to enable meaningful debugging
* **bootstrap and bridges:** WASHM uses a fixed FD (20251219) to bootstrap tight host/guest integration using JS eval; this leans on the fact that WASM code is trusted, and NEEDS full host access with least friction

### 1. The Launcher: `washm.js`

A single script that detects the runtime environment (`typeof window` vs `typeof process`) and initializes the WASM module.

*   **Node.js Path**:
    *   Uses `require('wasi')` (or `node:wasi`).
    *   Loads `.wasm` from the filesystem.
    *   Standard WASI implementation.

*   **Browser Path**:
    *   Uses `fetch` and `WebAssembly.instantiateStreaming`.
    *   **Minimal WASI Shim**: A hand-coded `wasi_snapshot_preview1` object with "Delegating Stubs".
        *   **`fd_write` (1/2)**: Defaults to `console.log` (buffered). Checks `globalThis.washm_wasi_overrides.fd_write` for upgrades.
        *   **`random_get`**: Defaults to `Math.random()` (sufficient for `HashMap` init). Checks `globalThis.washm_wasi_overrides.random_get`.
        *   **`clock_time_get`**: Defaults to `Date.now()`. Checks `globalThis.washm_wasi_overrides.clock_time_get`.
        *   **`fd_close`**: Implements the FD 20251219 trap to trigger `eval()`.
        *   **Others**: Return `ENOSYS` or `0` (Success) as minimally required for boot.

*   **Unified Bootstrap (FD 20251219)**:
    *   Both paths implement the special handling for FD 20251219.
    *   Writes to this FD are buffered.
    *   Closing this FD triggers `eval()` of the buffered string.

### 2. The Entry Point: `index.html`

Strictly minimal.

```html
<!DOCTYPE html>
<html>
<head>
    <meta charset="utf-8">
    <title>WASHM</title>
</head>
<body>
    <script type="module" src="./washm.js"></script>
</body>
</html>
```

### 3. Platform Detection: `src/platform.rs`

*   **Single Source of Truth**: A new module to detect and cache the environment type.
*   **Mechanism**: Executes `typeof window !== 'undefined'` via `eval_blocking` *once* at startup.
*   **Storage**: Uses `thread_local!` static `Cell<Option<Platform>>` to store the result (Node vs Browser). No locking required in single-threaded WASM.
*   **Usage**: `src/bridges/tty.rs` and other modules query this cached value instead of re-evaluating.

### 4. The Browser Bridge: `src/bridges/browser_tty.rs`

This Rust module is responsible for "upgrading" the browser environment from a console-logger to a full terminal emulator.

*   **Vendored Assets**:
    *   `xterm.min.js`
    *   `xterm-addon-fit.min.js`
    *   `xterm.css`
    *   Stored in `src/bridges/vendor/` and embedded via `include_str!`.

*   **Payload Construction**:
    *   Concatenates vendored JS/CSS.
    *   **UI Injection**: Creates `<style>`, `<div id="terminal">`, and `<link rel="icon">` elements. Sets initial `document.title`.
    *   **WASI Upgrade**: Overrides `globalThis.washm_wasi_overrides.fd_write` to pipe output to the xterm instance.
    *   **TTY Contract**: Implements `window.washm_tty` (read, enableRaw, size) to interface with xterm events.
        *   **Raw Mode**: In xterm.js, input is always "raw" (events). `enableRaw()` simply returns true and focuses the terminal. `disableRaw()` is a no-op or blur.
    *   **Events**: Hooks `term.onTitleChange` to update `document.title`. Enables `screenReaderMode`.

### 5. Filesystem & Other Bridges

*   **Filesystem**:
    *   **Node**: Uses native `wasi` (fs access).
    *   **Browser**: `washm.js` stubs `fd_open`, `fd_read`, `fd_seek`, etc., with `ENOSYS`.
    *   **Upgrade**: A future `src/bridges/fs.rs` will inject a browser-specific VFS bridge (backed by `sessionStorage` or `IndexedDB`) and override the WASI stubs in `globalThis.washm_wasi_overrides`.
*   **Other Syscalls**:
    *   All syscalls follow the same pattern: minimal stub in `washm.js` $\to$ full implementation injected by Rust bridge if needed.

### 6. Bridge Selection: `src/bridges/tty.rs`

*   **Detection**: Uses `platform::is_browser()`.
*   **Selection**:
    *   **True**: Calls `browser_tty::ensure_bridge()`.
    *   **False**: Calls `node_tty::ensure_bridge()`.

## Implementation Steps

1.  **Vendor Assets**: Download xterm.js assets to `src/bridges/vendor/`.
2.  **Refactor `washm.js`**: Implement the polyglot logic and delegating stubs.
3.  **Create `index.html`**: The minimal entry point.
4.  **Implement `src/platform.rs`**: The unified environment detection (thread-local).
5.  **Modernize `src/protocol.js`**: Rewrite to use `TextEncoder`/`Uint8Array` instead of Node.js `Buffer`.
6.  **Implement `src/bridges/browser_tty.rs`**: The injection and upgrade logic (including title/icon/raw mode).
7.  **Update `src/bridges/tty.rs`**: Use `platform::is_browser()` for dispatch.

## Verification & Smoke Tests

To ensure the browser implementation is robust and accessible, we mandate **manual verification by an LLM agent** using Playwright tools. The agent should use tools like `browser_navigate`, `browser_type`, and `browser_snapshot` (or inspecting the accessibility tree) to interact with the shell.

The tests rely on `xterm.js`'s `screenReaderMode`, which exposes the terminal contents to the DOM in a machine-readable format.

### Requirements

1.  **Enable Screen Reader Mode**: The `browser_tty.rs` bridge MUST initialize xterm.js with `{ screenReaderMode: true }`. This creates a `.xterm-accessibility-tree` DOM element containing the live terminal buffer.
2.  **Playwright Interaction**: The agent should target `.xterm-accessibility-tree` to read output and `textarea.xterm-helper-textarea` (or the terminal container) to send input.

### Mandatory Smoke Tests

The following scenarios must be verified by the agent:

1.  **Boot & Prompt**:
    *   **Action**: Navigate to `index.html`.
    *   **Check**: Inspect `.xterm-accessibility-tree` and confirm it contains the shell prompt (e.g., `washm$`).
    *   **Purpose**: Verifies WASM instantiation, bridge injection, and initial TTY rendering.

2.  **Basic Input/Output**:
    *   **Action**: Type `echo "hello world"` and press Enter.
    *   **Check**: Confirm `.xterm-accessibility-tree` contains the string `"hello world"`.
    *   **Purpose**: Verifies the async input loop (`WasmInputBackend`), raw mode handling, and stdout piping.

3.  **File Creation & Listing**:
    *   **Action**: Type `touch test_file` and press Enter. Then type `ls` and press Enter.
    *   **Check**: Confirm output contains `test_file`.
    *   **Purpose**: Verifies the VFS bridge, write permissions, and WASI syscalls (`fd_open`, `fd_readdir`).

4.  **Help Command**:
    *   **Action**: Type `help` and press Enter.
    *   **Check**: Confirm output contains a list of commands or usage information.
    *   **Purpose**: Verifies internal shell builtins and large output handling.

5.  **TTY Interaction (Cursor Movement)**:
    *   **Action**: Type `hello`, press `ArrowLeft` 3 times, type `X`.
    *   **Check**: Confirm the line reads `heXllo`.
    *   **Purpose**: Verifies that xterm.js correctly handles ANSI escape sequences generated by the shell's line editor.
