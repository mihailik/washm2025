# Ultra-Minification: JS Exile & _continue Exclusion

## Goal

Reduce washm.js to an absolute minimum launcher by moving all protocol logic into WASM-housed intelligence. The guest (Rust/WASM) bootstraps itself by writing JS code to a predefined fd at startup; the host evaluates this, dynamically installing all interop functionality. Eliminate `_continue` callback in favor of `_start` as the sole re-entry point.

**Final vision:** washm.js becomes a thin ~30–50 line bootstrap that:
1. Loads WASM
2. Sets up minimal WASI
3. Listens for guest writes to a known fd (e.g., fd 20251217)
4. Evaluates the JS code the guest writes there
5. That JS installs all protocol handlers (`/dev/host`, eval, fd translation, etc.) into the host

All protocol intelligence is authored in Rust/WASM, not hardcoded in the launcher.

## Current State

### washm.js (653 lines)

**Line breakdown:**
- ~50 lines: CLI arg normalization and WASM path resolution
- ~30 lines: WASI object setup (fs/env/preopens)
- ~20 lines: Memory access helpers and virtual fd map
- ~250 lines: WASI syscall wrapping (path_open, fd_write, fd_read, fd_close, path_filestat_get, fd_fdstat_get, etc.)
- ~50 lines: `/dev/host` path resolution and mounting logic
- ~200 lines: Eval protocol implementation (cookie state, JS execution, async handling, _continue callback)
- ~40 lines: Module loading and WASI instantiation

**Key responsibilities:**
1. **Bootstrap:** Load WASM, find paths, parse CLI args
2. **WASI wrapping:** Override syscalls to support `/dev/host` and `/dev/null`
3. **Virtual filesystem:** Translate guest fd→host in-memory objects (globalThis.mounted)
4. **Eval protocol:** Accept JS from guest, execute in host JS context, call `instance.exports._continue(cookie)` when done
5. **State management:** Track eval cookies, accumulate JS/JSON payloads per request

### `_continue` mechanism (current)

Guest writes JS to `/dev/host/eval/COOKIE.js` → host accumulates → host calls `instance.exports._continue(COOKIE)` → guest reads result from `/dev/host/eval/COOKIE.json`

## Phase 1: JS Exile

### Objective

Move all protocol logic (WASI wrapping, `/dev/host` mounting, eval state management, fd translation) from washm.js into WASM by having the guest author and inject JS code into the host at startup via a predefined fd.

### Key Changes

#### 1.1 Reserve a Known FD for Protocol Bootstrap

**Convention:** fd 20251217 (or configurable via env var)

At startup, the guest writes JS code to this fd. The host captures it and evaluates it immediately, installing all protocol handlers.

#### 1.2 Guest Generates Protocol JS at Startup

**In Rust/WASM guest (`embedded_brush_shell.rs` or similar):**

```rust
fn bootstrap_host_protocol() {
    // JS that implements all protocol logic:
    // WASI syscall wrapping and fixes,
    // /dev/host vfs, eval extras
    
    ... generate JS string ...
    fd_20251217.write_all(protocol_js.as_bytes()).unwrap();
}

#[no_mangle]
pub extern "C" fn _start() {
    ... initial startup logic ...
    bootstrap_host_protocol();
    ... rest of startup ...
}
```

#### 1.3 Reduce washm.js to Minimal Launcher

**New washm.js (~30–50 lines):**

```javascript
async function run() {
  ... find and load WASM ...
  ... setup minimal WASI ...

  // Capture protocol JS from guest via fd 20251217
  wasi.wasiImport.fd_write = (fd, iovs) => {
    if (fd === 20251217) {
      ... accumulate scriptJS ...
    }
    ...
  };

  ... instantiate ...

  // On fd_close(20251217):
  // eval(scriptJS), clear accumulated scriptJS -> creates a massive JS handling logic
}
```

#### 1.4 Current JS Complexity Moves into Guest-Generated Protocol

All the logic currently in washm.js (~250+ lines of WASI wrapping, eval handling, fd translation) is now authored in Rust and emitted as JS string at startup:
- WASI wrapping functions
- `/dev/host` resolver
- Eval cookie state machine
- Virtual file descriptor map
- JS execution sandbox

This JS is injected into host at startup in the new model.

## Phase 2: _continue Exclusion → _start as Entry & Re-entry Point

### Objective

Eliminate `instance.exports._continue` callback entirely. `_start` becomes both the entry point (first call) AND the re-entry point for eval completion. Host calls `_start` multiple times: once to initialize, then again each time an eval result is ready.

### Key Changes

#### 2.1 _start State Machine: Entry vs. Re-entry

**Architecture:**

```rust
#[no_mangle]
pub extern "C" fn _start() {
    if is_initial_boot {
        ... bootstrap_host_protocol() ...
        ... run shell/app ...
    } else {
        ... handle re-entry (eval completion) ...
    }
}
```

**Flow:**
1. Host runs WASI which invokes `_start()` → normal startup path (largely nothing there)
2. Guest requests eval: writes JS to fd 20251217, closes it
3. Host's fd_close hook evaluates JS
4. JS that is evaluated calls `_start()` whenever it wishes, up to Rust to produce the right behavior
5. `_start` is triggering future's polling and resuming execution


#### 2.3 Complexity of the Rust build with semi-hijacked WASI

By default _start in Rust performs certain initialisations. In the new world these need to be moved out of _start into a separate function that can be called once at the beginning of execution.

The build will need to re-declare _start and the implementation need to use a static mutable variable (no locks, no syncs, just flat static mutable) to detect the first entry and fork the logic.

The re-entry path needs to be involved in the async executor polling loop to ensure that futures are polled correctly and on time.

The build needs to make sure NOT to invoke any shutdown sequences upon exit of _start. The standard WASI build might be injecting code doing it, so this needs to be carefully verified.

Given the _continue had a cookie parameter, and _start has none, the logic to trigger corresponding continuation/completion needs to re-target from an argument to another option. A simple approach would be to directly write to the WASM memory at a predefined set address. Given that both the eval'ed JS and WASM are controlled from the same Rust that is not a problem.

#### 2.4 Old JS eval bridge

The old eval bridge relied on vfs /dev/host/eval/... and we should stop doing it. That shift removes a whole bunch of string allocation and should keep things more efficient.

Some more research needs to be done to find how Rust handles continuations: does it poll all outstanding futures, or only those that are somehow "elegible". And if the latter, we should establish a viable pattern to manage that eligibility marker.

#### 2.5 Remove _continue from Export Table

**Before:**
```rust
#[no_mangle]
pub extern "C" fn _continue(cookie: u32) { /* old callback */ }
```

**After:**
- Deleted entirely
- Host never calls it
- Reduces WASM binary by ~100–200 bytes
- Only `_start` is exported

# Summary

The change should substantially simplify the host.

Apart from improving safety and consolidating the platform, that should help future cross-platform efforts, especially for the browser case.
