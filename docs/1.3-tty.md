# 1.3 TTY integration (Terminal behavior via eval)

This document defines a minimal, launcher‑agnostic approach for full terminal support (raw mode, arrow keys, mouse, resize, bracketed paste, etc.) for the WASM-native guest. It is explicitly constrained so that no changes should be required in the `axy.js` launcher: any complex JS logic should come from injected snippets from Rust via `/dev/host/eval` and/or VFS-based event/response flows.

## Key tenets
- The launcher remains minimal — it offers only a VFS overlay and calls `_continue(cookie)` after eval or VFS responses.
- The guest (Rust) injects JS snippets via `eval` to implement terminal-specific host logic.
- Large snippets reside in JS files adjacent to the corresponding Rust module; .js file naming conventions live next to `tty.rs` or the module that owns the terminal logic.
- Tiny one-line JS snippets that set a single property may be embedded inline in Rust (string literals).
- No host-side checks are performed (e.g., `process.stdin.isTTY`) beyond minimal try/catch guards — the launcher should not add brittle checks or policy logic.
- The implementation is made to EMULATE THE NORMAL TERMINAL within NORMAL APIs, not to provide a new custom API.

## File layout & inclusion conventions
- Put JS files next to Rust modules using the `include_str!` macro in Rust.
  - Rust code example:
    ```rust
    const RAW_ENABLE_JS: &str = include_str!("./tty/raw-enable.js");
    let res = crate::wasm_async::eval_blocking(RAW_ENABLE_JS)?;
    ```
- Keep snippet files small and focused; each snippet should return a JSON-like object with `ok: true/false` and additional info.

## Communication model
- One-off operations (short and simple): Use `/dev/host/eval`.
  - Guest writes JS snippet, host runs `eval`, writes `cookie.json` and calls `_continue(cookie)`.
  - Use this for simple, immediate toggles like `setRawMode(true)`, toggling mouse, or performing a one-shot query (e.g., clipboard read).
- Event registrations and streaming: Use `eval` to register host-side listeners that write event JSON payloads into VFS paths (e.g., `/dev/host/events/<cookie>/<n>.json`) and call `_continue(cookie)` when new events are available.
  - Example: `process.stdout.on('resize', () => { write to /dev/host/events/cookie/*.json; instance.exports._continue(cookie) })`.
- Synchronous queries with structured response: Use a blocking VFS or `eval` that returns JSON; Rust may call `eval_blocking` to receive the response.

## Event payload format (recommended)
- Keep JSON fields consistent and compact.
- `resize` events: `{ type: 'resize', columns: number, rows: number, ts: <ms since epoch> }`.
- `mouse` events: `{ type: 'mouse', kind: 'move'|'press'|'release', button?: 'left'|'right'|'middle', x: number, y: number, ts: <ms> }`.
- `key` events (if chosen to be reported via VFS): `{ type: 'key', seq: <raw-string>, ts: <ms> }`.
- `ok`/`error` reply objects: `{ ok: true }` or `{ ok: false, error: "..." }`.

## Rust-side Terminal API
- Implement an exact one-to-one emulation of the standard Rust terminal, making code using the standard terminal compile as is, with no changes.

- Implement `RawModeGuard` RAII:
  - Constructing the guard triggers `enable_raw_mode` (via `eval`/inline snippet).
  - Dropping the guard triggers `disable_raw_mode`.

## Implementation details & patterns
- Embedding JS: Use `include_str!("./raw-enable.js")` for complex snippets and embed trivial ones inline.
- Polling / waiting on host reply: Use the existing continuation `_continue(cookie)` mechanism — use `WasmHostFuture` or similar `vfs_blocking` helper for blocking flows. For event streams use `vfs` event files + `_continue(cookie)` to wake the guest.
- Parsing key events: Prefer reading raw bytes from WASI stdin while in raw mode and implement a comprehensive parser in Rust for escape sequences (arrow keys, modifier keys, bracketed paste sequences, mouse sequences); that is independent of host changes.
- Mouse: Use both approaches where appropriate:
  - Simple terminal reporting: the guest parses mouse sequences from stdin (commonly used Xterm sequences).
  - Alternatively, for advanced (native OS) mouse events, inject host listener `mouse-enable.js` to register and report richer events (optional, via VFS/event mechanism).

## Testing & fallbacks
- Provide tests covering basic scenarios:
  - `enable_raw_mode()` toggles and returns ok json.
  - Key sequences arrive over stdin when in raw mode and the parser correctly maps them to events.
  - `size()` returns expected structure when called with simple `eval` snippet.
  - For CI or non-TTY environments, ensure the API gracefully returns errors and fallback behaviors (non-raw/blocking mode).

## Host-only specifics: minimal & robust
- The host should not implement logic beyond necessary VFS/eval handling and `_continue` semantics.
- Avoid precondition checks; do `try/catch` around risky host calls, return errors as JSON. Do not prevent the guest from attempting actions.
- We assume host is `node` (for now), and will maintain minimal code required to integrate with WASI.


## Documentation & developer workflow
- Keep the evaluated JS snippets as separate files adjacent to the Rust caller to aid maintenance (vs. inline code forever).
- Use `include_str!` in Rust to bundle them and write tests that ensure the snippet hasn't regressed.

## Notes on security & trust
- This design assumes the guest is trusted to execute host-side JS snippets (the same project controls both sides).

## Conclusion
- This approach achieves the stated goal: full feature support with zero launcher policy changes, everything injected via `eval` or VFS eventing.
- It is practical and incremental; it starts with raw-mode and stdin-based key parsing and scales to full `crossterm` features via eval scripts and a small Rust library.
