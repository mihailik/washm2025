To implement **Generational ID Management** in practice, we need to transition from a "Sequential Vector" model to a "Relational Arena" model. The goal is to ensure that a `FuncId` or `LocalId` obtained at the start of a transformation remains valid even if we inject 100 new functions or parameters in the middle.

Here is a 4-step strategic plan to deliver this in washm-engine.

---

### Step 1: The Infrastructure (The `washm-arena`)
We shouldn't just use `u32` aliases. We should use **Generational Indices**. A generational index consists of an `index` and a `generation`. If an item at index `5` is deleted and a new one is added, the generation increments, making the old ID effectively "null" rather than pointing to the wrong data.

*   **Suggestion:** Implement a lightweight `Arena<T>` in `src/collections/arena.rs` (or use a crate like `id-arena`).
*   **The Types:**
    ```rust
    pub struct FuncId(u32, u32);   // (index, generation)
    pub struct LocalId(u32, u32);  // (index, generation)
    pub struct GlobalId(u32, u32); // ...
    ```

---

### Step 2: Unifying the "Callable" Space
In Wasm, indices for functions start with Imports, followed by internal Functions. This "shared space" is the #1 cause of index-shift bugs.

*   **Suggestion:** Create a unified `Function` structure in the IR that handles both Imports and Definitions, similar to Walrus.
*   **The Change:** 
    *   Currently, `washm` has `module.imports` and `module.functions` as separate vectors.
    *   The new model: `module.functions` is a single `Arena<Function>`, where a `Function` variant determines if it's an `Import` or a `LocalDefinition`.
    *   **Benefit:** `FuncId` 0 is always the first function, regardless of whether it's an import or a local stub.

---

### Step 3: Function-Local Scoping (Locals)
Locals are the most volatile part of Wasm. Adding a single parameter to a function shifts *every* `local.get` and `local.set` in the body.

*   **Suggestion:** Move the local variable storage into a `LocalArena` *inside* the `Function` struct.
*   **The API Change:**
    ```rust
    // OLD
    builder.local_get(5); // What is local 5? Who knows.

    // NEW
    let my_var = func.add_local(Type::I32);
    builder.local_get(my_var); // Stable, even if params are added later.
    ```

---

### Step 4: The "Finalization/Layout" Phase
Since the `.wasm` binary format *strictly requires* sequential indices, we need a bridge between our stable IDs and the final binary output.

*   **The Strategy:** The `BinaryWriter` should not just iterate over the arena. It must first calculate a **Layout Map**.
*   **The Process:** 
    1.  Collect all active IDs in the arena.
    2.  Sort them (Imports first, then Definitions).
    3.  Create a `Map<FuncId, u32>` (Stable ID -> Final Wasm Index).
    4.  During emission, the writer replaces every `FuncId` with its mapped `u32`.

---

### Why this is Viable:
1.  **Non-Breaking (Internal):** We can implement the `Arena` logic *inside* the `Module` while keeping the external `get_function_mut` API the same during the transition.
2.  **Safety:** It prevents "Ghost References" where an optimization pass deletes a function but another pass accidentally keeps a reference to its index.
3.  **Parallelism:** Multiple passes can now work on different parts of the `Module` simultaneously without coordinating on index shifts.

### My Recommendation for the First Move:
Don't refactor everything at once. Start by refactoring **`GlobalId`**. Globals are global-scope but rarely deleted or reordered compared to functions. It's the perfect "sandbox" to test the `Arena` infrastructure before touching the high-stakes `Function` and `Local` logic.
