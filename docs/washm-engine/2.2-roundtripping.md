# Roundtripping and Dogfooding with washm-engine

Here is a refined implementation plan to prioritize dogfooding and architectural consolidation. By enhancing washm-engine to handle custom sections and DWARF metadata natively, we transform it from a "Batch Optimizer" into the "Surgical Tool" required for the Distiller.

### Refined Plan: The Integrated Distiller

This plan moves the heavy lifting into washm-engine while using washm-test as the specialized consumer. We will maintain the AST IR (Tree IR) but augment it with sufficient "environmental awareness" to allow transparent roundtripping.

#### Phase 1: Infrastructure (The "Walrus-fication" of washm-engine)

We need to make the engine "lossless" for binary data it doesn't intend to transform.

1.  **Custom Section Preservation**:
    *   Define `CustomSection` in ir/module.rs.
    *   Update binary_reader.rs to capture `Payload::CustomSection` into a `Vec<CustomSection>` in the `Module`.
    *   Update binary_writer.rs to emit these sections, ensuring they are preserved during roundtrips.

2.  **DWARF Ingestion**:
    *   Integrate `gimli` into binary_reader.rs.
    *   During the code section pass, map the current `wasmparser` offset to DWARF source lines.
    *   Attach `DebugLocation` to newly created `ExpressionId`s via the `AnnotationStore`.

3.  **DWARF Reconstruction**:
    *   Update binary_writer.rs to track the binary offset of every instruction emitted.
    *   Implement a DWARF generator that uses these new offsets and the `AnnotationStore` to rebuild the `.debug_line` section.

#### Phase 2: The "Frontier Shift" (Surgical IR Manipulation)

Instead of manual byte patching, we use the engine's stable IDs to manipulate the module structure.

1.  **Global/Data API**:
    *   Implement `Module::find_export_global(&self, name: &str) -> Option<GlobalId>`.
    *   Implement `Module::add_data_segment(&mut self, offset: i32, data: Vec<u8>) -> DataId`.

2.  **Memory Awareness**:
    *   Ensure binary_writer.rs automatically updates `Memory.initial` if the new data segments or the shifted `__heap_base` require more pages than the original binary.

#### Phase 3: The Coverage Pass (AST-to-AST Transformation)

We implement the instrumentation as a standard washm-engine `Pass`.

1.  **`CoverageInstrumentationPass`**:
    *   **Scan**: Identify all functions that have DWARF line information.
    *   **Inject**: For every unique source line in a function, find the corresponding `ExpressionId` and wrap/prepend the coverage probe (load-increment-store).
    *   **Patch**: Locate `__WASHM_COV_PTR` (exported by the guest) and set its initial value to the address of our injected DMZ.

#### Phase 4: The Distiller CLI (washm-test)

The washm-test crate becomes a lightweight wrapper around the engine.

1.  **CLI implementation**:
    *   Read `.wasm` -> `washm::ir::Module`.
    *   Apply `CoverageInstrumentationPass`.
    *   Run `washm::wasm::BinaryWriter` -> `.distilled.wasm`.
2.  **Verification Utility**:
    *   Use `llvm-dwarfdump` and `wasm-objdump` in automated tests to verify that `__heap_base` shifted and DWARF locations point to the correct new offsets.

---

### Key Technological Decisions

*   **Tree IR for Instrumentation**: While `walrus` uses a flat stream, we will use the `ExpressionId` in the Tree IR. Instrumentation will be performed by replacing an expression with a `Block` containing the original expression plus the probe.
*   **Gimli as the Map**: We use `gimli` only for reading/writing the DWARF sections; washm-engine remains the owner of the instructions.
*   **Wasm-Encoder for Layout**: We will leverage `wasm-encoder`'s ability to build sections, but we must provide it with the correct serialized bytes for our reconstructed DWARF.

# PleasResearch Binaryen DWARF fidelity

> When Binaryen drives its optimisation phases,
> does it maintain dwarf fidelity through the phases?

The answer is **yes, but with significant internal complexity**.

Binaryen maintains DWARF fidelity by treating the DWARF sections as a parallel data structure that must be "relocated" once the code is transformed.

### How Binaryen Maintains Fidelity

1.  **Address Mapping**: During ingestion, Binaryen records the **original binary offsets** for every expression. It correlates these with the address ranges in the DWARF sections (like `.debug_line` and `.debug_info`).
2.  **Location Tracking**: The IR retains "debug locations" (file, line, column) as annotations on expressions.
3.  **The "Re-Emission" Phase**:
    *   This is the critical part. Since Binaryen uses a **Tree IR**, the final binary layout of instructions will almost certainly be different from the input, even if no optimizations were run (due to how it flattens the tree back into a stack machine).
    *   Binaryen tracks the **new binary offsets** of every expression as it is written out.
    *   It then iterates through the DWARF metadata and replaces every "Old Address" with its corresponding "New Address."

### Limitations & Caveats

*   **Version Pinning**: Binaryen is traditionally most stable with **DWARF 4**. While it supports DWARF 5, the complexity of updating `.debug_line_str` and other newer sections can sometimes lead to less-than-perfect fidelity.
*   **Lossy Serialization**: Because Binaryen deserializes the DWARF into an internal representation (`DWARFYAML`), it can lose some original byte-level formatting or highly specialized vendor-specific DWARF extensions.
*   **Inlining & Structural Changes**: When Binaryen inlines a function, it has to perform complex surgery on the DWARF "Subprogram" entries and "Inlined Subroutine" scopes to ensure backtraces still look correct. This is where most "fidelity loss" occurs—it's often computationally impossible to perfectly represent every optimized-away variable's lifecycle.

---

### Comparison with our Plan for washm-engine

Our plan for the Distiller (as outlined in 2.2-roundtripping.md) actually follows a similar philosophy but aims for **higher "surgical" fidelity** by using the `gimli` crate:

*   **Our Advantage**: Since we are non-negotiably sticking to a **Tree IR** and we are the authors of the `BinaryWriter`, we can integrate the location mapping *directly* into the emission loop. 
*   **The Difference**: Binaryen often treats DWARF as an "afterthought" to be patched at the end. We are planning to treat DWARF as a **first-class annotation** that is inseparable from the `Expression`.

### Verification for washm-engine
To reach Binaryen-level fidelity, we must implement:
1.  **Custom Section Passthrough**: So that the actual DWARF strings and type info (`.debug_str`, `.debug_info`) are preserved even if we only modify the addresses (`.debug_line`).
2.  **Instruction-to-Address Mapping**: A robust way to store the final `u32` offset of every expression during emission.

## Plan: Refined Phase 1 — Foundations of Surgical Roundtripping

This plan transforms washm-engine into a "surgical" tool by enabling lossless handling of custom sections and providing the infrastructure for high-fidelity DWARF preservation through AST transformations.

### TL;DR
We are moving away from the "Lossy Batch Optimizer" model. By the end of Phase 1, washm-engine will be able to ingest a WASM module, preserve its custom sections (DWARF, build IDs, etc.), and maintain internal links between IR expressions and their original source locations. This sets the stage for the Distiller's instrumentation while ensuring the resulting binary remains fully debuggable.

---

### Steps

#### 1. Implement Lossless Custom Section Registry
*   **Module Definition**: Add `pub custom_sections: Vec<CustomSection>` to `Module` in ir/module.rs.
*   **Infrastructure**: Define `CustomSection` struct to hold the section name and raw byte payload.
*   **Reader Integration**: Update `BinaryReader` in wasm/binary_reader.rs to capture `Payload::CustomSection` instead of ignoring it.
*   **Writer Integration**: Update `BinaryWriter` in wasm/binary_writer.rs to emit these sections in the correct order (usually after the code section).

#### 2. DWARF-to-IR Ingestion (The Mapper)
*   **Dependencies**: Add `gimli` to Cargo.toml.
*   **Offset Tracking**: Modify `BinaryReader` to record the `wasmparser` binary offset for every instruction it processes.
*   **Line Map Ingestion**: Implement a helper that uses `gimli` to parse `.debug_line`.
*   **Annotation**: As the `BinaryReader` creates `ExpressionId`s, it will look up the current offset in the DWARF map and attach a `DebugLocation` to the expression via `module.annotations`.

#### 3. Precise Emission Trajectory
*   **Offset Recording**: Enhance `BinaryWriter` in wasm/binary_writer.rs to track its own internal write-offset.
*   **Mapping Store**: Create a temporary map `ExpressionId -> NewBinaryOffset` during the emission of the Code section.
*   **Fidelity Requirement**: This mapping must be byte-accurate, accounting for the variable-length LEB128 encodings of the final WASM output.

#### 4. The DWARF Relocator (Initial implementation)
*   **Logic**: Implement a DWARF generator (using `gimli`'s writing capabilities) that:
    1.  Reads the original DWARF sections from the `custom_sections` registry.
    2.  Iterates through the DWARF line sequences.
    3.  Uses the `ExpressionId -> NewBinaryOffset` map to update the addresses in the `.debug_line` table.
*   **Emission**: The `BinaryWriter` replaces the original DWARF custom sections with these updated versions in the final output.

---

### Verification
*   **Roundtrip Parity Test**: Create a test where a WASM binary with DWARF is read and immediately rewritten. Use `llvm-dwarfdump` to verify that all line information is identical.
*   **Custom Section Integrity**: Verify that non-standard custom sections (e.g., `producers`, `target_features`) survive the roundtrip untouched.
*   **Location Consistency**: Verify that `module.annotations.get_location(expr_id)` matches the information produced by `wasm-tools dump --dwarf`.

---

### Decisions
*   **Choice: `gimli` over `wasm-tools`**: We chose `gimli` for its lower-level control, which is necessary for the surgical "relocation" strategy compared to the higher-level but more rigid abstractions in `wasm-tools`.
*   **Choice: AST-Native Mapping**: We rejected a separate "sidecar" map. Location data is stored directly in `AnnotationStore`, ensuring that if an optimization pass clones or moves an expression, the location moves with it automatically.
