
# Testing in WASM — Design & PoC

**Goal:** Run repository tests using the same launcher/wasm runtime infrastructure so tests behave like `cargo test` while respecting the project's WASM-only, async-first constraints.

## 1. Constraints & Assumptions
- No multithreading inside the guest (single-threaded WASM). Tests may run sequentially in-process.
- Blocking reads in the guest are strongly discouraged — prefer non-blocking/reactor-friendly patterns. Small, well-scoped blocking is possible in dedicated worker isolates but not the norm.
- No `wasm-bindgen`; raw ABI/WASI-style imports and exports are used. The project uses a reactor pattern (`_continue`) and a tokio current-thread runtime in `entry::run_async`.
- Host (Node/launcher) is available and trusted to perform actions not possible in WASM (e.g., process-level isolation, spawning other node processes and loading WASM instances).

## 2. High-level Design

Two-layer architecture: an in-WASM test harness and a Host Orchestrator.

- In-WASM Test Harness
  - Discovers and runs tests compiled into the WASM module.
  - Runs tests sequentially (single-threaded) by default.
  - Supports async tests by driving them on an in-wasm executor (reuse the existing tokio current-thread builder used by `entry::run_async`).
  - Captures stdout/stderr via the same capture mechanism used by `libtest` (`io::set_output_capture`) and marshals captured output into per-test results.
  - Exposes a deterministic entrypoint (e.g., `run_tests()` export that returns encoded JSON results or writes structured results to a memory buffer the host can read).

- Host Orchestrator (Node / `washm.js` launcher)
  - Loads the test-enabled WASM module and calls `run_tests()` (or per-test entrypoints) to execute tests.
  - Provides per-test isolation when needed by spawning a new host process that re-loads the WASM module and runs a single test (simulates `libtest`'s spawn-subprocess/abort behavior). Use env var like `__RUST_TEST_INVOKE` to indicate single-test mode (mirrors libtest behavior).
  - Collects JSON/structured results, prints them in familiar `cargo test` format and exits with appropriate code.

## 3. Compatibility Notes (libtest review)

- Threads: `libtest` uses `thread::spawn` to run tests concurrently; when host platform lacks threads it falls back to synchronous execution. Therefore sequential in-process execution works without fundamental changes.
- Blocking/waiting: `libtest` uses `mpsc::recv`/`recv_timeout` to await test completions. For single-thread operation this is safe (test runs synchronously and then sends completion). If non-blocking behavior is required, the harness can be adapted to a futures/poll-based model or provide a host-driven event loop.
- Process isolation and panic modes: `libtest` supports `panic=abort` mode by spawning subprocesses for tests. WASM can't spawn OS processes; the host simulator (Node) should provide the equivalent behavior by launching a fresh Node process that loads the WASM to run the single test (this matches your idea of host-based isolation).
- Panic/unwind: Not all wasm targets support unwinding. Tests that rely on catch_unwind or unwinding behavior should either be run with host isolation (so abort-mode semantics apply) or limited to unwinding-capable targets/builds.

## 4. Interface & UX

- Build step: `cargo test --target wasm32-wasip1 --no-run` or via `cargo build --features wasm-test --target wasm32-wasip1` to build a test-enabled WASM artifact.
- Run step (host): `node tools/wasm-test-runner.js target/wasm32-wasip1/debug/washm.wasm` (example). The runner loads WASM, invokes the `run_tests` export, streams results and sets exit code.
- Optionally provide a `cargo wasm-test` wrapper that automates build+run and exposes the familiar `cargo test` flags (filter, --nocapture, --test-threads, etc.).

## 5. Output & Reporting

- Test results should be returned as structured JSON from WASM to the host, containing per-test: name, result (ok/failed/ignored/timed out), exec time, stdout bytes, failure message.
- Host translates the structured results into console output (pretty/terse/json/junit) and exit codes consistent with `cargo test` expectations.

## 6. Security & CI

- Running tests in CI: CI should compile the WASM test artifact and run the host orchestrator. For tests that need isolation, CI should use the host-per-test mode (spawns fresh Node processes). Set timeouts for tests and enforce resource limits.

## 7. Trade-offs & Risks

- Pros: Keeps tests running under the same launcher, supports async tests cleanly, minimal changes for most unit tests.
- Cons: Per-test process isolation is a host-side emulation (extra complexity), some `libtest` features (native threads, certain panic/unwind behavior) require host-side emulation or test restrictions.

## PoC: Minimal, low-friction proof-of-concept

Goals for PoC:
- Demonstrate running #[test] and async tests in-wasm via an exported `run_tests()` entry.
- Support both in-process sequential mode and host-based per-test spawn mode for abort-mode tests.
- Produce `cargo test`-like console output (a simple Pretty formatter is sufficient for PoC).

PoC Design & Steps

1. Harness crate
	- Add a small crate in the workspace (e.g., `wasm-test-harness`) or a module behind a `wasm-test` feature.
	- Use `libtest-mimic` or a tiny custom runner to register and run tests; prefer `libtest-mimic` for simpler integration.
	- Implement `#[no_mangle] pub extern "C" fn run_tests(ptr: u32, len: u32) -> u32` (WASI/ABI-friendly variant), or simpler: `pub fn run_tests() -> String` if the host loader can call Rust exports directly and read result memory. Return a JSON string with test results.
	- Internally: discover tests (static test vector), run them sequentially; for async tests, run them on a tokio current-thread executor.
	- Capture stdout/stderr using `io::set_output_capture` and include captured bytes in JSON.

2. Host runner
	- Add `tools/wasm-test-runner.js` using the existing launcher/loader to load the `.wasm` and call `run_tests()`.
	- For per-test spawn simulation: host accepts `--spawn-single <testname>` and when provided launches a child node process (same script) with an env var `__RUST_TEST_INVOKE=<testname>` and the wasm file; the child runner detects the env var and runs just that test; child returns result via exit code and writes output.

3. Example test
	- Add `tests/poctest.rs` or use an inline test; include one sync test and one async test that uses the tokio runtime so we validate async handling.

4. Commands to build & run (PoC)
```
cargo build -p washm --target wasm32-wasip1 --no-default-features --features wasm-test
node tools/wasm-test-runner.js target/wasm32-wasip1/debug/washm.wasm
```

5. Success criteria
	- `run_tests()` returns structured results for both sync and async tests.
	- Host prints results similar to `cargo test` and exits with non-zero code on failures.
	- Per-test spawn mode runs the requested test in a fresh process and returns expected status.

6. Next steps after PoC
	- Add `cargo wasm-test` wrapper and integrate flags (filter, --nocapture, --format=json/junit).
	- Add CI job that runs the test pipeline and verifies exit status and JSON outputs.
	- Improve harness to fall back to non-blocking/polling loops if desired for stricter reactor compatibility.

## 8. Open questions
- Do we want strict single-thread-only semantics enforced at compile time (feature flag)?
- How important is full `libtest` parity (edge-case semantics for thread-run concurrency), vs. a pragmatic harness that covers most tests? My recommendation: prioritize practical coverage (async tests, output capture, CI reporting), and add compatibility shims as needed.
