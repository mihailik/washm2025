# 1. WASM Asynchronous Interop Specification (WASI-Async)

This document defines the architecture and communication protocol for a multi-language WASM environment where asynchronous operations are dispatched from the guest module to the native host runtime using a custom Virtual File System (VFS) and a continuation mechanism.

## 1.1 Architecture Overview

The system is designed to allow multiple heterogeneous WASM modules (Rust, Brush (Rust shell, see `brush-fork/`), QuickJS) to coexist and share a single Host Event Loop for asynchronous I/O and computations (specifically JavaScript execution).

The system is split into three layers:

1.  **Host Runtime (Canonical):** The native environment is **Node.js** — the host executes JS payloads written to `/dev/host/eval` and is responsible for calling back into guests with `_continue`.

  Execution Model (Canonical):
  - JS payloads written to `/dev/host/eval/{cookie}.js` are executed inline by the host runtime. The canonical execution method is to syntactically verify with the `Function` constructor and—if valid—evaluate inline. If the `Function` constructor fails with a `SyntaxError` (for example due to top-level `await`), the host then executes the code via an `AsyncFunction` constructor. The host captures return values or promise fulfillment/rejection and writes the JSON result to `/dev/host/eval/{cookie}.json`. Synchronous execution results will be written back BEFORE the WASM execution continues with _continue() call.
  - The host calls the exported WASM function `_continue(cookie: i32)` to notify the guest that a result is available.
  - The host must not write into WASM memory; guests read the JSON result using-standard WASI file I/O.

  Trust Model (Canonical):
  - The guest is given the facility to execute JS intentionally, by design, to allow full access to host's abilities; these JS payloads are executed inline in order to allow the access to the host's internal state.
  - Sandboxing of these JS payloads is prohibited.

  Note: QuickJS, Brush, and Rust are expected to run as *guests* inside WASM modules. QuickJS is used inside WASM only as a guest (compiled with Asyncify), not as the host.
2.  **Communication Layer:** The WASM imports/exports, VFS mounts, and memory access logic used for request/response handling.
3.  **WASM Guest Modules:** The compiled language runtimes (Rust, Brush, QuickJS) which implement their language-native asynchronous infrastructure (`Future`, `async`/`await`, Asyncify) on top of the common communication layer.



The core principle is that the WASM guest drives the REPL and program logic. It reads stdin using standard WASI I/O (`_start` or `_initialize`) and runs its own REPL. The Host (Node.js) acts as a passive launcher: it executes JS payloads written by guests to the VFS (`/dev/host/eval`) and calls the single required export `_continue(cookie)` to notify the guest when the results are available. The Host MUST NOT write to WASM memory or call guest allocators.

## 1.2 The Communication Protocol

The entire asynchronous model relies on two core, non-WASI-standardized interfaces: a Virtual Filesystem (VFS) mount for the request, and an exported function for the response.

### 1.2.1 The Virtual Filesystem (VFS) Mount: `/dev/host/eval`

This VFS mount serves as the primary **request channel** for the WASM guest to initiate host execution (e.g., running JavaScript code). The Host Runtime must intercept all WASI calls to this path.
IMPORTANT: The `/dev/host/eval` mount MUST be virtual-only. Hosts MUST NOT map (`preopen`) `/dev/host/eval` to any real host filesystem path. Instead, the host must implement a virtual/in-memory filesystem overlay for this mount and handle reads/writes via interception logic.

| Attribute | Value | Description |
| :--- | :--- | :--- |
| **Mount Point** | `/dev/host/eval` | The special path intercepted by the Host Runtime's VFS handler. |
| **Mount Mode** | `virtual-only` | MUST NOT be preopened or mapped to host directories; host must implement an in-memory VFS for this mount. |
| **Request File** | `{id}.js` | WASM writes the JS payload to this file. `{id}` is the **Continuation Cookie** (a 32-bit unique identifier). |
| **Response File** | `{id}.json` | WASM later reads the JSON result or error from this file. |
| **Payload (Write)** | Raw JavaScript source code (UTF-8). | The content of the file is the JS code the host must execute (e.g., `1+2`). |
| **Result (Read)** | JSON string. | The stringified result of the JS execution, or a standardized JSON error object if the execution fails. |

**Process Flow (WASM $\to$ Host Request):**

1.  WASM generates a unique 32-bit `cookie_id` (used as the primary key for the continuation).
2.  WASM uses WASI functions (`path_open`, `fd_write`, `fd_close`) to write the JS content to `/dev/host/eval/{cookie_id}.js` on the virtual VFS exposed by the host.
3.  The Host intercepts these calls, extracts the JS payload and the `cookie_id`.
4.  The Host schedules the JS execution on its native event loop, storing the `cookie_id` to link the result back to the correct WASM waiting context.
5.  The WASM module then internally pauses its specific language runtime's thread of execution (via `Poll::Pending`, `Future.set_result`, or stack unwinding).

### 1.2.2 The Host-Called Export: `_continue`

This WASM export is the primary **response channel** for the Host to signal completion back to the guest. It is the Host's equivalent of a callback function.

| Attribute | Value | Description |
| :--- | :--- | :--- |
| **Exported Function** | `_continue` | Must be exported by *all* WASM guest modules (Rust, Brush, QuickJS) with this exact signature. |
| **Signature** | `(func (param i32)) -> ()` | Takes a single 32-bit integer parameter (cookie id). |
| **Parameter** | `i32` cookie id | The host passes the cookie id (32-bit integer). The guest reads `/dev/host/eval/{cookie}.json` to obtain the response; the Host must not write into WASM memory.

> **Note:** The canonical launcher does not include `axy_submit` as a host-driven entrypoint. Guests run their REPL and read stdin directly. Any legacy or compatibility host entrypoint should be provided as an optional guest-side shim using the VFS (write + cookie) pattern.

**Process Flow (Host → WASM Continuation, canonical):**

1. The Host's native event loop task (e.g., JS execution) completes.
2. The Host prepares the response (JSON result/error) and writes it to `/dev/host/eval/{cookie}.json`.
3. The Host calls the exported function `_continue(cookie)` to notify the guest.
4. The WASM module receives `_continue(cookie)`, opens `/dev/host/eval/{cookie}.json` using WASI file I/O, reads the result, and wakes the appropriate continuation.

See `host/node-host/host.js`, `host/node-host/README.md`, `src/wasm_async.rs` and `smoke_test_node.js` for a reproducible smoke test. QuickJS build helpers are in `tools/quickjs_build.js`; Brush is included as a submodule under `brush-fork/`.

Security / compliance note: The Node host PoC implements the `/dev/host/eval` VFS as a virtual-only in-memory overlay by default (no host directory mapping). Older versions of the PoC used a host directory for development convenience; that dev-mode mapping has been removed for security compliance. Production hosts MUST NOT map `/dev/host/eval` to a real host filesystem path.

## Security Modes and Sandbox Clarification

- Canonical (Trusted) Mode:
  - The canonical, specification-compliant mode assumes the guest is trusted.
  - Sandboxing of guest-supplied JS is explicitly prohibited in this mode to allow the guest full access to the host's capabilities and state.
  - Hosts claiming canonical compatibility MUST expose the `/dev/host/eval` VFS as virtual-only and must *not* isolate eval execution from the host process or internal state.

- Optional Untrusted/Isolated Mode:
  - Host implementations MAY optionally offer a separate "untrusted" or "isolated" execution mode that restricts guest capabilities (for example, using Node's `vm` module, worker threads, or separate processes).
  - This mode is *not* canonical, and hosts must document behavioral differences, restrictions, and compatibility caveats (including differing semantics for `/dev/host/eval` and restricted host API access).
  - When running untrusted guests or public multi-tenant workloads, use the isolated mode and do not expect canonical-level behavior or compatibility guarantees.

Note: The PoC host in this repository implements the canonical model by default and does not enable isolation. Any sandbox or isolation techniques applied must be documented and acknowledged as non-canonical.

Host VFS Implementation Pattern (pseudo):
1. Maintain an in-memory map keyed by cookie id (string/number) where each entry contains the request JS text and the JSON result.
2. Intercept WASI file operations under `/dev/host/eval` (path_open, fd_write, fd_read, fd_close) and route them to the in-memory map (do not forward to or touch the host filesystem).
3. When the host sees a completed `.js` write for `{cookie}.js`, schedule execution on its event loop and store the result in the in-memory `{cookie}.json` value.
4. When the host completes execution, call guest `_continue(cookie)`; the guest will use standard WASI I/O to read `/dev/host/eval/{cookie}.json` (the host will serve the content from the in-memory map during the guest's read).

**EXPLICIT NOTE**

Sandboxing of these JS payloads is prohibited. They must allow WASM access to host capabilities and internal state, as this is the core trust model of the architecture.


This PoC demonstrates a straightforward launcher enabling WASM guest by exposing JS as a capability. The eval VFS flow is the canonical control plane for host interop.

### 1.2.3 The Preopen Filesystem

The host should reflect the host filesystem 1:1 into the guest via preopens. This means:

- POSIX hosts: the host root `/` maps to `/` in the guest.
- Windows hosts: each drive letter (e.g., `C:`) should be preopened as `/C:/` in the guest (e.g., host `C:\Users\alice` → guest `/C:/Users/alice`). UNC shares should be mapped under `/UNC/` (e.g., host `\\server\share\dir` → guest `/UNC/server/share/dir`).
\
Note: There is a special exception to these preopen semantics: the `/dev/host/eval` mount is an implementation-defined, virtual-only VFS and MUST NOT be preopened or mapped to any host filesystem path.

The Host must preserve the semantics and canonicalization of host paths (case sensitivity, permissions), and must not silently rewrite path structures beyond a 1:1 mapping necessary for runtime interoperability.


# 2\. WASM Asynchronous Interop: Language-Specific Integration

This section details how the Rust, Brush, and QuickJS runtimes must adapt their internal asynchronous infrastructures to utilize the shared `_continue` and VFS protocol defined in the architecture specification.

## 2.1 Brush Integration

Brush (the Rust-based shell included as a submodule at `brush-fork/`) must be compiled with WASI support to serve as the canonical frontend. The primary integration point is the Brush runtime hooking into the WASM host interop pattern — i.e., using the VFS (`/dev/host/eval`) and the exported `_continue(cookie)` to schedule host-side JavaScript or system calls.

### A. The Brush Startup Flow

The host runtime should initialize Brush as the primary shell interface where appropriate.

1. **Initial Call:** Host calls the WASM module's standard WASI entry point (`_initialize` or `_start`).
2. **Brush Init:** The WASM code executes the Brush runtime, initializing the shell environment and hooking its async runtime to the Axy continuation map.
3. **Hook Registration:** Brush must register any necessary helper functions (e.g., `host_eval`) that write to `/dev/host/eval/{cookie}.js` and return a Rust `Future` that resolves when `_continue` is invoked by the host.
4. **Executor Integration:** Brush's async runtime (for example a `Future`-based executor compatible with wasm32-wasi) should integrate a Continuation Map (Waker-based) to pause and resume shell coroutine execution when awaiting host results.
5. **Exiting:** Brush should gracefully enter an idle state and call WASI `proc_exit(0)` when asked to quit, returning control to the host.

### B. Brush Continuation Pattern

Brush must adopt the same continuation pattern as Rust guests: use a `cookie_id` based Continuation Map to map blocked `Future`s to their wakers, write host-eval JS to `/dev/host/eval/{cookie}.js` and be able to react to `_continue(cookie)` by reading `/dev/host/eval/{cookie}.json` and waking the corresponding task.

Note: CPython/Xonsh integration remains optional and is out of scope for the initial Brush-first delivery. If/when Xonsh is reintroduced as a guest, it should follow the same continuation pattern as Brush and Rust (Continuation Map + `_continue` callback).

## 2.2 Rust Integration

Rust utilizes the `std::future::Future` trait and a global `Waker` map to implement its continuation logic.

### A. The Rust Executor / Continuation Map

1.  **Continuation Map:** A global, thread-safe (e.g., `Arc<Mutex<HashMap<u32, Waker>>>`) map that stores the `cookie_id` to the blocked Future's `Waker`.
2.  **`WasmHostFuture` Struct:** A custom `struct` that implements `std::future::Future`:
      * On its first `poll()`, it generates the VFS request, stores the current `Waker` in the Continuation Map, and returns `Poll::Pending`.
      * Subsequent `poll()` calls check a shared status flag.

### B. Handling `_continue` (Rust)

The Rust implementation of `_continue(cookie_id)`:

1.  Accepts the `cookie_id` parameter (i32) and uses it to locate the result at `/dev/host/eval/{cookie_id}.json`.
2.  Reads the response JSON from `/dev/host/eval/{cookie_id}.json`.
3.  Looks up the `Waker` in the Continuation Map using the `cookie_id`.
4.  Sets the Future's result data (making it available for the next `poll`).
5.  Calls **`waker.wake()`**. This signals the Rust runtime to re-poll the blocked Future, which then returns `Poll::Ready(result)`.

## 2.3 QuickJS Integration

QuickJS must be compiled with **Asyncify** enabled. This shifts the complexity from the language runtime to the compiler.

### A. Asyncify Configuration

1.  **Compiler Flag:** The QuickJS compiler/toolchain must be invoked with `-s ASYNCIFY`.
2.  **JS Async Hook:** A function must be exposed to the QuickJS environment that wraps the VFS I/O calls:

<!-- end list -->

```javascript
// Function made available inside QuickJS via Host linkage
function host_eval_async(js_code) {
  return Asyncify.handleAsync(async () => {
    // 1. Generate cookie
    const cookie = get_unique_cookie_id();
    
    // 2. Perform synchronous WASI write to VFS
    wasm_write_file(`/dev/host/eval/${cookie}.js`, js_code);
    
    // 3. Suspend and return control to host
    const result_json = await wasm_wait_for_continue(cookie);
    
    // 4. On resume, read and return the JSON
    return JSON.parse(result_json);
  });
}
```

### B. Handling `_continue` (QuickJS)

When the host calls `_continue(cookie)`:

1.  The `_continue` function accepts the cookie id parameter and notifies QuickJS-in-WASM that the VFS result is ready.
2.  It notifies the QuickJS-in-WASM runtime that the asynchronous VFS operation associated with that `cookie_id` is complete.
3.  The QuickJS runtime uses Asyncify's internal mechanisms to restore the saved stack frame, allowing the `host_eval_async` function to proceed past the `await wasm_wait_for_continue(cookie)` call and return the result.

## 2.4 Brush Hooks (Example)

To bridge the execution contexts, Brush can register helper functions or Rust-native commands that wrap the underlying Rust/QuickJS initializers and async helpers. Below is a minimal Rust pseudo-example that shows how to create a `host_eval` wrapper returning a `Future` resolved via `_continue`:

```rust
// Pseudo-Rust example exposed inside Brush runtime
async fn host_eval(js_code: &str) -> Result<Value, EvalError> {
  // 1. Generate cookie
  let cookie = unique_cookie_id();

  // 2. Write JS payload to `/dev/host/eval/{cookie}.js` (WASI write)
  wasm_write_file(format!("/dev/host/eval/{}.js", cookie).as_str(), js_code.as_bytes()).await?;

  // 3. Suspend and wait for `_continue` to be called by the host
  let result_json = wasmhub_wait_for_continue(cookie).await; // resolves when host writes {cookie}.json

  // 4. Return parsed result
  Ok(serde_json::from_str(&result_json)?)
}
```

Register such a helper in Brush so scripts and prompts can `await host_eval("1+2")` inside Brush coroutines.

To bridge execution contexts, guests should register lightweight interop wrappers to call into other runtimes (Rust/QuickJS/Brush) using the Continuation Map pattern described above. For Brush, use the pseudo-Rust `host_eval` helper shown earlier. For QuickJS, rely on Asyncify with the `host_eval_async` wrapper.
