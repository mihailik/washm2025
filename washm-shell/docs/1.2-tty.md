# TTY & Input Handling Overhaul (Status: Partially Implemented)

## Architecture: The JS/WASM Bridge (Implemented)
The bridge acts as the backend for the shell and other input-consuming commands.

## The Directive (Active)
We are enforcing a strict **WASM-only, Async-only** architecture for terminal interaction.
- **No Native Support:** The codebase is treated as a WASM guest artifact. Native execution paths are dead code.
- **No Blocking:** Input operations must never block the main thread. `read_line` is fundamentally async.
- **No `reedline`:** We discard the synchronous `reedline` library. We implement our own async "cooking" (line editing).
- **No `wasm-bindgen`:** We use raw ABI imports/exports and the reactor pattern (`_continue`).

### 1. Initialization & Loading (Implemented)
- **Lazy Load:** On the first input request, Rust `eval`s the bridge JS source (loaded via `include_str!`). Avoid IIFE unless necessary.
- **Source Maps:** The evaluated string passed from Rust should be expanded to include `//# sourceURL=washm-tty-bridge.js` for DevTools visibility (do NOT include in the JS file).
- **Host Setup:** The JS logic:
  - Assesses the environment (TTY vs Pipe).
  - Switches to raw mode if applicable.
  - Latches onto `stdin` 'data' events.
  - Exposes a global/scoped function for subsequent async reads.

### 2. Async Data Flow (Implemented)
- **Rust Side:** Calls the exposed JS function to "await next data".
- **JS Side:**
  - If data is buffered, returns immediately.
  - If empty, registers a callback. When `stdin` data arrives, it invokes the callback (triggering `_continue` in the reactor).
- **Payload:** Returns chunks of data (single keystrokes or pasted batches).

## Rust-side Implementation Layers

### Layer 1: Async Character Stream (Implemented)
- A low-level async function/stream that calls the JS bridge.
- Handles the `eval` vs. "call named function" logic.
- Returns raw `String` or `Vec<u8>` chunks.

### Layer 2: The Cooked Logic (OUTSTANDING)
- A reusable async function/struct that consumes the Layer 1 stream.
- **Responsibilities:**
  - Cursor movement (Left/Right).
  - Text insertion/deletion (Backspace/Delete).
  - History navigation (Up/Down).
  - **Ctrl+C:** Intercepts and returns `Interrupted`.
  - **Exclusions:** No complex Vim/Emacs modes (Ctrl+D, etc.) initially.
- **Output:** Writes ANSI sequences to `stdout` to reflect state.

### Layer 3: The Unified Backend (Partially Implemented)
- The component exposed to `brush`.
- **Mode Selection:**
  - **Interactive:** Uses Layer 2 (Cooked Logic).
  - **Piped:** Bypasses cooking; buffers Layer 1 stream until `\n`.
- **Startup/Shutdown:**
  - Initializes the bridge on first use.
  - Ensures raw mode is disabled on drop/exit via a bridge cleanup call.

## Build System Integration (Implemented)
We adhere to the `build.rs` rewriting model. **Do not modify vendor files directly.**
1. **Inject Payload:** The new async implementation resides in `src/wasm_interactive.rs` (in the workspace). `build.rs` copies this to `OUT_DIR` during build.
2. **Patch Traits:** Use `build.rs` regex replacement to convert `InputBackend::read_line` in `interactive_shell.rs` to an `async fn`.
3. **Patch Call Sites:** Use `build.rs` to update `run_interactively` loops to `.await` the result of `read_line`.
4. **Shim Modules:** Patch `brush-interactive/src/lib.rs` to alias `ReedlineInputBackend`, `BasicInputBackend`, etc., to our new `WasmInputBackend`.

## Brush Integration & Startup (Implemented)
We replace the fragmented backend logic (`Reedline`, `Basic`, `Minimal`) with a single, unified **`WasmInputBackend`**.

### 1. Unified Backend Strategy
- **One Backend to Rule Them All:** We inject `src/wasm_interactive.rs` which defines `WasmInputBackend`.
- **Shims:** We export `WasmInputBackend` as `ReedlineInputBackend`, `BasicInputBackend`, and `MinimalInputBackend` in `brush-interactive/src/lib.rs`. This satisfies `brush-shell`'s startup logic without changing `entry.rs` significantly.
- **Mode Selection:** The backend detects the environment (via the JS bridge) and configures itself:
  - **Interactive:** If `isatty`, enables raw mode and uses the async line editor.
  - **Piped:** If not `isatty`, buffers input until newline.

### 2. Startup Adjustments
- **`brush-shell/src/entry.rs`:** No changes needed to the selection logic itself because we alias all options to our unified backend.
- **Initialization:** The first call to `read_line` (or `new`) in the backend initializes the JS bridge.
- **Shutdown:** The backend ensures raw mode is disabled when dropped or when the shell exits.

### 3. Crossterm Shim
- **`src/tty/crossterm_shim.rs`:** Maps `enable_raw_mode`, `disable_raw_mode`, and `size` to our JS bridge.
- **Event Reading:** Redirects any blocking `crossterm::event::read` calls to our async `next_event` stream (though ideally, we replace the caller entirely).

## Outstanding Implementation Plan: The "Cooked" Layer

This section outlines the steps to close the gap in Layer 2, implementing elegant, lightweight line editing.

### Principles
*   **Zero Dependencies:** No heavy terminal crates (e.g., `termion` or `crossterm` events) in the critical path. We parse what we need.
*   **Strictly Async:** The "Read" phase waits for host events; the "Update" phase is synchronous and instant.
*   **Simplicity:** Use a predictable state machine.

### Step 1: Mode Detection (Critical Safety)
Before entering any loop, `read_line` must permit a fallback.
- **Logic:** Calls `washm_tty.enableRaw()`.
- **If Fail/False:** Assuming Piped Mode. Loop `read()` until `\n`. Return plain string.
- **If Success:** Enter Interactive Mode (Step 2).

### Step 2: Input State Machine
Replace character-by-character processing with an event parser.
- **Structure:** `enum Event { Char(char), Arrow(Dir), Esc, Backspace, Enter, Ctrl(char) }`
- **Parser:** A state machine that absorbs `ESC`, then `[`, then `A/B/C/D`.
- **Flow:** `async fetch_raw_chunk() -> parse_into_events() -> process_event()`.

### Step 3: The Line Editor State
Replace `String` buffer with a cursor-aware struct.
- **Struct:** `struct LineBuffer { chars: Vec<char>, cursor: usize }`
- **Operations:**
  - `insert(char)`: Insert at `cursor`, increment `cursor`.
  - `delete()`: Remove at `cursor - 1`, decrement `cursor`.
  - `move(n)`: Clamp new position between `0` and `len`.

### Step 4: History Management
- **Store:** `Vec<String>` in `WasmInputBackend`.
- **Navigation:**
  - **Up:** Push current buffer to "draft", load older entry.
  - **Down:** Load newer entry (or restore "draft").

### Step 5: Rendering (The "Update" Phase)
Do not use incremental updates (too complex/fragile). Use "Clear & Redraw Line".
- **Sequence:**
  1. `\r` (Carriage Return to start).
  2. Print `Prompt + Buffer`.
  3. `\x1b[K` (Clear to screen end).
  4. Calculate visual cursor position.
  5. `\x1b[{N}D` (Move cursor Left to correct spot).
- **Optimization:** Only flush `stdout` once per event loop cycle.

### Step 6: Tab Completion (Bonus)
- If the shell passes a completion handler, invoke it on `Tab`.
- Render suggestions below the prompt (requiring the prompt to be redrawn after).
