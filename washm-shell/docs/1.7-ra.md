This specification outlines the transition of the `build.rs` rewrite engine from regex/string-matching to a semantic model using `rust-analyzer` (RA).

### 1. Objective

Replace the current brittle 350+ lines of path-patching and regex replacements with a **Semantic Transformation Engine**. This engine must programmatically resolve module hierarchies and update `crate::` references based on their new position in the project's module tree.

### 2. Execution Environment: Deadlock Avoidance

The primary implementation constraint is preventing Cargo lock contention.

* **Target Directory Redirection:** The tool must programmatically set `CARGO_TARGET_DIR=target/ra-rewrite` (or a similar isolated path) before initializing the RA `ProjectWorkspace`.
* **Reasoning:** If RA attempts to discover the project using the default target directory, it will attempt to acquire the same `package-cache` lock held by the currently running `cargo build`. This results in a permanent deadlock.
* **Implementation:** ```rust
std::env::set_var("CARGO_TARGET_DIR", "target/ra-rewrite");
// Only then initialize ProjectWorkspace::load
```


```



### 3. The Dual-Graph Architecture

The implementation must maintain two concurrent views of the codebase to bridge the gap between "Source" and "Target" states.

* **Source View (The "Shadow Graph"):**
* Initialize an `AnalysisHost` and load the upstream fork directories (e.g., `brush-fork/brush-core/src/lib.rs`) into the Virtual File System (VFS).
* **Constraint:** These must be defined as valid `CrateRoot` entities in a temporary `CrateGraph`. This allows RA to resolve references like `crate::tty_helpers` (referring to sibling files in the fork) within the fork's own context.


* **Target View (The "Project Graph"):**
* Initialize the host project's `CrateGraph`.
* **Transformation:** Attach the files in `target/vendor/` not as crates, but as `Module` nodes under the host project’s root crate.



### 4. Core Transformation Requirements

#### A. Semantic Re-rooting (Fixing `crate::` paths)

The team must implement a pass that updates internal paths.

* **Problem:** Code in `target/vendor/brush-core/main.rs` that says `use crate::tty_helpers;` will fail because it now looks for `tty_helpers` at the host project's root.
* **RA Solution:** 1. Identify the original `FileId` of the reference in the Shadow Graph.
2. Query the Project Graph for that `FileId`'s new position relative to the host root.
3. Programmatically rewrite the path to its qualified form: `crate::brush_core::tty_helpers`.

#### B. Automated Path Synthesis

Replace the manual `pathdiff` and `replace("\\", "/")` logic.

* **Logic:** When a `mod` declaration in the Project Graph refers to a file that remains physically located in the `brush-fork/` directory, the engine must use RA’s `SourceMapper` to calculate the distance.
* **Output:** Automatically emit the `#[path = "..."]` attribute based on the VFS location.

#### C. Type-Aware Structural Search and Replace (SSR)

Replace the `ast_grep_replace_batch` with RA's SSR.

* **Requirement:** Target specific patterns like `NotSupportedOnThisPlatform($msg)` only when they originate from the vendored error types.
* **Validation:** Retain the `verify_no_stubs` check to ensure the final disk output is clean.

### 5. Implementation Directives

1. **VFS-to-Disk Sync:** Perform all transformations in the VFS memory first. Only write to `target/vendor/` once the semantic model is consistent.
2. **Reference Case:** The implementation is successful when `crate::` references in the vendored shell resolve to their siblings in the `target/vendor` tree without manual string manipulation or regex guessing.

### 6. Line Count Target

The implementation should reduce the total line count of `build.rs` from ~460 lines to approximately **250 lines** by centralizing all patching logic into a single semantic loop, while shifting the complexity into the RA initialization boilerplate.


# Semantic rewrites

After inspecting `build.rs`, it is clear that **almost all** rewrites should move to a semantic approach. While simple string replacements exist, the vast majority of the current logic is actually a manual, fragile attempt to simulate what **`rust-analyzer` (RA)** does natively.

The current script is essentially a "Regex-based Compiler," and moving to RA allows us to replace guesswork with **Symbolic Certainty**.

### 1. The "Almost All" Semantic Transition

The following sections of the `build.rs` are prime candidates for the semantic approach defined in `1.7-ra.md`:

* **Global `crate::` Re-rooting (Semantic):** the old script currently use a complex `crate_re` with per-match logic to guess if a reference is internal or cross-crate.
* **RA Approach:** Use symbol resolution. RA knows exactly which crate a symbol belongs to. We simply tell RA to qualify any symbol that resolves to the "Shadow Graph" (the fork) with the new host path.


* **Module Path Resolution (Semantic):** the old script has ~40 lines of code dedicated to finding `.rs` or `mod.rs` files and calculating `#[path]` attributes.
* **RA Approach:** This is RA’s core job. The `SourceMapper` identifies the file location of a `mod` declaration automatically, rendering the manual file-system probes obsolete.


* **Async Color Propagation (Semantic):** the old script currently use a `call_re` to find `.read_line(...)?` and append `.await`.
* **RA Approach:** As established, use a semantic crawler to identify the entire call chain. This ensures we don't miss a call just because it doesn't match whatever specific regex pattern (e.g., if it doesn't end in a `?`).


* **Stub Replacement (Semantic):** the old script target specific files like `users.rs` or `network.rs` to replace "NotSupported" errors.
* **RA Approach:** Instead of file-specific branching, use `find_all_references` on the `NotSupportedOnThisPlatform` variant. This catches platform-specific stubs wherever they occur, across all crates, in a single pass.



### 2. What remains as SSR?

A few "Search and Replace" tasks in the script are still best handled by **Structural Search and Replace (SSR)** because they involve specific code-style migrations rather than global symbol tracking:

* **Doc Comment/Attribute Stripping:** Replacing `//!` with `//` or commenting out `#![...]`. These are purely structural changes at the file level.
* **Inlining Modules:** The old existing logic for inlining the `refs` module in `brush-interactive` is a structural swap that SSR handles more cleanly than a raw semantic edit.

### 3. Summary of Implementation Shift

| Current Logic in `build.rs` | Recommended Method | Benefit |
| --- | --- | --- |
| **Manual `crate::` prefixing** | **Semantic Resolution** | Eliminates negative lookahead/regex guessing. |
| **Manual `pathdiff` for `#[path]**` | **`SourceMapper`** | Handles Windows/Unix paths and `mod.rs` natively. |
| **Hardcoded `read_line` regex** | **Call Graph Crawler** | Guarantees all async callers are patched. |
| **File-specific stub patching** | **`find_all_references`** | Simplifies 100+ lines of `if path.ends_with(...)`. |

### 4. Direction for the Team

The directive should be: **"Semantic by default, SSR by exception."**

The developers should not write another `if path.ends_with(...)` block. Instead, they should write **Transformation Passes** that run across the entire `Vfs`.

1. **Pass 1:** Resolve and fix all `crate::` and `use` paths.
2. **Pass 2:** Crawl and "Asyncify" the input/output call chains.
3. **Pass 3:** Find all references to "NotSupported" errors and replace with host stubs.

This transition will successfully shrink your `build.rs` from its current complex state down to the **~250 line target** by removing the repetitive file-walking and string-matching boilerplate.

# Shim call site discovery

Below is an actionable transform plan that uses RA to convert `read_line` to `async` across vendored crates; next I’ll list exact files, AST edits, batching, validation and rollback steps.## Plan: Convert `read_line` to async across vendored brush crates ✅

**TL;DR — Use rust-analyzer (RA) semantic queries** in build.rs to precisely find every `read_line` trait, impl, and call site, then apply controlled AST edits (trait → `async`, impls → `async` or shims, callsites → add `.await`), with validation and small, reversible batches to minimize blast radius. This fixes runtime mismatches and keeps transformations safe and testable.

## Steps 🔧

### 1. Discover all `read_line` references using RA
Run RA symbol/reference queries for `read_line` across workspace and vendored crates. Record exact locations (e.g., input_backend.rs trait, impls in `brush-fork/brush-interactive/src/*`, callsites such as interactive_shell.rs).


### 2. Transform (batch 1)

In build.rs add an AST transform that **converts the trait declaration** in input_backend.rs from `fn read_line(...) -> Result<...>` to `async fn read_line(...) -> Result<...>`, and simultaneously convert all impls found in the RA reference list (add `async` to `fn` and adjust return types).

### 3. Transform (batch 2)

Add AST rules in build.rs to add `.await` to every `read_line` callsite (MethodCallExpr, UFCS, CallExpr) within `brush-*` interactive modules; also ensure enclosing functions are made `async` where necessary.

### 4. Validation & safety

After each batch, run `npm run build` (vendored copy), and run a validation pass in build.rs that fails the build with a helpful message if:
   - Any `read_line` callsite in interactive crates lacks `.await`, or  
   - Any `impl` signature does not match the trait signature.

### 5. Handle edge cases

For external/third-party impls or unavoidable sync backends, add a small synchronous shim on `crate::wasm_interactive::WasmInputBackend` that implements the synchronous signature by invoking the async implementation safely (documented and limited to wasm build).

### 6. Rollout & tests

Apply in small increments (trait + first crate → build → iterate). Add a compile-only integration test that compiles transformed `brush-interactive` and a unit that asserts no `read_line` callsite is unawaited.

### Exact files & symbols to change 📁
- Primary trait change:
  - input_backend.rs — convert `fn read_line(...) -> Result<ReadResult, ShellError>` to `async fn read_line(...) -> Result<ReadResult, ShellError>`.
- Primary impls to update (found via RA references):
  - `brush-fork/brush-interactive/src/minimal/*` (`MinimalInputBackend`),  
  - `brush-fork/brush-interactive/src/reedline/*` (`ReedlineInputBackend`),  
  - `brush-fork/brush-interactive/src/basic/*`, and any other impls RA reports.  
- Callsites to update:
  - interactive_shell.rs and all `MethodCallExpr`, UFCS, and free-call sites within `brush-*` interactive modules.  
- Build-time transform location:
  - build.rs — add AST-based rules using `ra_ap_syntax` / `SyntaxEditor` to (a) edit trait + impl `fn` nodes to `async fn`, (b) wrap call expressions with `.await` as needed, (c) implement the validation pass.

### Validation & failure modes (harsh to reality — precise checks) ⚠️
- Add a post-transform check: fail with a list of file:line locations when a `read_line` call lacks `.await` in interactive modules.  
- Fail if any `impl` method signature does not match the (new) trait signature.  
- Keep transforms reversible by recording applied edits and offering a single-commit revert or a `--dry-run` mode in build.rs.

### Further considerations (short) 💡
- Risk: Changing trait signature touches many impls; mitigate by atomic trait+impl batches and quick builds.  
- Edge cases: UFCS and macro-generated calls can be missed — expand RA queries to include PathExpr and CallExpr forms and add a final heuristic search.  
- Rollback: Keep changes in build.rs (vendoring stage) only — repository vendor files remain unchanged and transformations are reversible.
